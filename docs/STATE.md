# Project state

## Audit (2026-10-15, before the reliability work)

What existed (commit `0d29680` snapshot):
- UI screens: home, alarm setup, sleep mode, stats, settings, sounds, lights, onboarding,
  local login/signup (plaintext passwords in SQLite, no backend, login gated the app).
- Modules: sleep-analysis (audio + accel features), alarm-engine, notifications, sound,
  Hue/Yeelight lights, bedtime calculator, i18n en/fr, SQLite profile/sessions.
- 5 jest test files, but no `test` script. `tsc` had 1 error (DevToolsScreen).

What did **not** work:
- **The alarm could not fire reliably**: it relied on JS `setTimeout`/`setInterval`.
  The native `AlarmModule` it called did not exist, `AlarmEngine.initialize()` was never
  called outside the dev screen, and nothing consumed the trigger. App killed, Doze or
  screen off meant no alarm.
- **No motion was recorded at night** in production. The accelerometer and microphone
  were only wired in the dev screen. `expo-background-task` was installed but unused.
- Smart-wake logic counted light epochs rather than consecutive ones (bug), and was never fed data.
- No morning summary beyond a "last night" card holding only the duration.
- This clone was missing 8 commits from origin (tracked `android/`, release CI, SDK 57
  fixes). They were merged into the work below.

## After this work

- Native local module `modules/smart-alarm` (Kotlin):
  - fallback alarm via `AlarmManager.setAlarmClock` (exact, Doze-proof, app-killed-proof,
    re-armed after reboot/time change);
  - foreground service recording the accelerometer all night (wake lock);
  - native wake decision inside the window, ringing service plus a lock-screen activity.
- JS: night analysis (calm/light/wake estimate), summaries stored in SQLite, new home,
  sleep mode and night summary screens. The login gate is removed (the code is kept).
- See `docs/SCIENCE.md` for the rationale and limits.

## Known limits

- Phone movement is only a rough sleep-stage proxy (see SCIENCE.md).
- If the phone is on the bedside table, nothing moves: the alarm rings at the target time.
- If the tracking service is killed (aggressive OEM battery savers), the smart part is
  lost but the fallback alarm still rings. Disable battery optimisation for the app.
- Legacy modules (lights, sounds, auth, onboarding quiz) are unchanged and not part of
  the core flow.

## Audit lot 1 (shipped in 1.4.4)

From the 16/11 audit (B1 to B5). Pure transition rules in `AlarmPolicy.kt`, tested
by `AlarmPolicyTest.kt`:
- **B1** a ringing whose process dies (empty battery, crash, kill) stayed `ringing` forever
  and blocked auto mode. The state is now closed (`done`) at boot, when an alarm is received,
  in `rearm`, and by a "watchdog" probe armed during the ringing (30 min without a live ringing
  or a pending snooze). A pending snooze is re-armed at boot.
- **B2** a smart wake before the target (6:40 for 7:00) no longer rings again at 7:00: the target
  served by a ringing less than 3 h earlier is consumed.
- **B3** direct boot: alarm prefs in device-protected storage (`Prefs.kt`, migration
  at first unlock), `LOCKED_BOOT_COMPLETED`, alarm components `directBootAware`,
  React Native loaded only after unlock (`MainApplication.kt`).
- **B4** zero days selected: already disarmed on master; test added, Sleep API and probes also turned off.
- **B5** reopening the app no longer clears the evening probes (only if the target changes).

Dead code removed (import graph from `index.ts`/`App.tsx`, 0 orphan files left):
Login, Signup, Onboarding, EnrichedOnboarding, AlarmSetup, SleepAnalysis, DevTools screens;
`alarm-engine`, `auth`, `notifications`, `bedtime-calculator` modules; animation components
and hooks, `constants`, `navigation/types`. Left for a next batch: unused dependencies

## Limits / to validate

- Not yet validated on a real night or on a test device.
- The Sleep API depends on Play Services and on the (optional) `ACTIVITY_RECOGNITION` permission.
- Phone actigraphy does not really distinguish sleep phases: the expected gain is modest
  (see `docs/SCIENCE.md`).
- Dawn light on a phone screen is well below the 250-300 lux of the studies.
- Doze and manufacturer task killers can delay the probes: ask users to ignore battery optimisations.
- The torch points at the mattress when the phone lies screen-up: off by default.
- The sleep-onset score can trigger during bedtime reading with the phone still: the sleep onset is then estimated too early.
